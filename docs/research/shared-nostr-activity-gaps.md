# Shared Nostr plugin: Activity integration gaps

Originally researched 2026-09-08 against upstream main. Historical findings below are not the current integration status. As of 2026-09-09, Nostr PR #26 contains the transport implementation and acknowledgement fix; five local Activity integration tests pass through the shared plugin. Production deployment remains unverified. See [the infrastructure readiness guide](../activity-infrastructure.md).
The shared repository's current main is [`ef34a58`](https://github.com/NEARBuilders/nostr.nearbuilders.org/tree/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e), also the target of the September 2 [`@every-plugin/nostr@1.1.0` release](https://github.com/NEARBuilders/nostr.nearbuilders.org/releases/tag/%40every-plugin%2Fnostr%401.1.0). Activity's protocol currently references 1.0.0; that does not establish which plugin artifact a running host has loaded.

## What already exists

| Capability | Existing behavior | Activity implication |
| --- | --- | --- |
| Signed event publishing | `publishEvent` accepts arbitrary integer kinds. `StandardAdapter.publishSigned` verifies the signature and returns success per relay. | Kind 1701 needs no new event-format endpoint. Activity must require a positive acknowledgement from its intended durable relay before completing its reservation. |
| Raw event queries | `queryEvents` supports kinds, authors, IDs, time bounds, and generic tag filters converted to `#tag`. | Activity's `s`, `t`, `n`, and `i` filters already fit. The public maximum is 500; Activity scans 1,000. |
| Internal subscriptions | `StandardAdapter.subscribe` calls the pool and supports event/EOSE callbacks and close. | It is comment-specific (kinds 1111 and 1, target tags) and is not exposed in the contract. |
| Lifecycle cleanup | `StandardAdapterLive` uses scoped acquire/release and invokes `adapter.close()`. | Cleanup is not entirely missing. The implementation closes configured relays, whereas requests can also open override relays. |
| Backend credential building blocks | The client sends `x-api-key`; middleware contains `requireAuthOrApiKey` and permission-checking `requireApiKey`. | `publishEvent` currently uses `requireAuth`, which requires both user and userId. Whether a particular API key supplies those depends on the host. Key-only publishing is not explicitly contracted or proven. |
| NEAR identity binding | Public reads, signed kind-27235 challenge verification, and wallet KV write preparation already exist. | Mutation routes derive the account from the signed-in user's primary NEAR account, while Activity must bind the specific Activity Source account. |

## Exact required changes in nostr.nearbuilders.org

1. **Make the actual relay configuration explicit and consistent.** Raw operations use `standardRelays` derived from `STANDARD_RELAYS`; `listRelays` reports a separate `relays` value. Align these or expose their distinct purposes accurately, and point Activity publish/query/subscription at the same approved relay set. Defaults currently use nos.lol, relay.damus.io, and relay.primal.net for standard operations, plus nearbuilders.communities.buzz.xyz for Buzz. The README's suggestion that `variables.relays` controls raw routes does not match this implementation. [Configuration](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/plugins/nostr/src/lib/nostr-config.ts), [root configuration](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/bos.config.json), [README](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/plugins/nostr/README.md).

2. **Expose a general live-event stream.** Add `subscribeEvents` using the same raw filter model, a service method, and an adapter subscription without comment restrictions. Define reconnect/resubscribe with overlap replay and event-ID deduplication, and cancel subscriptions, timers, and all opened sockets on caller cancellation and plugin shutdown. The existing pool is created without reconnect enabled; its resolved dependency defaults reconnect to false. Specify recovery across both relay disconnections and plugin/client connection loss. [Existing adapter](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/plugins/nostr/src/nostr-core/adapters/standard.ts), [dependency lock](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/bun.lock), [nostr-tools pool defaults](https://github.com/nbd-wtf/nostr-tools/blob/fed4a5561398a93dfae0663089b7196e4d6e534f/abstract-pool.ts#L64).

3. **Provide strict, bounded raw reads.** Remove the `rawQuery` catch-to-empty behavior and return typed unavailable/timeout failures. Merely removing that catch is insufficient: `querySync` resolves collected events on close, and the pool counts failures toward completion. Use actual successful EOSE with an independent deadline to distinguish complete empty history from failure or partial results. Raise the supported scan cap to at least 1,000, or implement equally safe complete pagination; document cap behavior so Activity can fail loudly instead of skipping records. Preserve same-second records and inclusive `until` semantics. [Service fallback](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/plugins/nostr/src/services/nostr.ts#L236), [pool querySync](https://github.com/nbd-wtf/nostr-tools/blob/fed4a5561398a93dfae0663089b7196e4d6e534f/abstract-pool.ts#L293), [pool close handling](https://github.com/nbd-wtf/nostr-tools/blob/fed4a5561398a93dfae0663089b7196e4d6e534f/abstract-pool.ts#L179), [Activity transport and scan behavior](../../api/src/activity/activity-relay.ts).

4. **Accept source-signed events without an additional Nostr API key.** The earlier recommendation to add a publish-permission API key was withdrawn. PR #26 makes raw `publishEvent` available without a user session while validating the event signature and restricting destinations to configured relays. Activity still authenticates event producers with its own source-scoped API keys before signing. Existing comment and binding mutations retain their authentication requirements. Relay authentication is a separate deployment policy; the standard transport does not implement NIP-42 authentication.

5. **Prove the integration through the plugin runtime and compiled artifact.** PR #26 has passing coverage for signed kind-1701 publishing, acknowledgement failures, tag filters, bounded queries, live reconnect/replay, cancellation and compiled WebSocket operation. Local Activity tests additionally exercise feed pagination on small histories, provenance, Redis scoring and replay. Existing comment compatibility coverage and production capacity validation remain separate gates. The plugin must be released and the deployed Activity host configured to use that verified version before production cutover.

## Optional binding consolidation

Binding changes are not required just to move relay transport. If moving source binding too, expose account-explicit helpers with authorization for the exact source account, and preserve Activity's confirmation that FastNear returns the intended source public key before activating the Signing Identity. Do not replace source history with a current user identity lookup. The shared reader currently casts stored KV values without schema validation and collapses fetch failures to null; strict binding confirmation should distinguish unavailable data from absence and validate the stored shape. [Binding route context](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/plugins/nostr/src/index.ts#L63), [KV reader](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/plugins/nostr/src/lib/fastnear-kv.ts), [Activity protocol](../activity-protocol.md).

## Relay infrastructure and what remains in Activity

The inspected plugin tree establishes a relay client, not a bundled relay server with durable storage. Its Railway file deploys the everything-dev runtime image. Existing public relays are configured by default, so deploying a new relay is not inherently necessary; a selected relay must still meet Activity's durability, query capacity, rate-limit, and operational requirements. [Repository tree](https://github.com/NEARBuilders/nostr.nearbuilders.org/tree/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e), [Railway configuration](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/ef34a58ca5ae2f2c2e680956e4d5cd191ea3830e/railway.toml), [production requirements](../activity-protocol.md#production-requirements).

A DNS lookup from this research environment on September 8 failed to resolve `relay.nearbuilders.org`; `nostr.nearbuilders.org` resolved to Cloudflare addresses. This is a scoped observation, not proof about every network or a deployed relay's history. Earlier conversation treated `relay.nearbuilders.org` as an established service without verification.

Activity keeps source approval, encrypted signing identities and rotation history, source API keys, durable source-scoped idempotency reservations, event provenance validation, Redis projections, scoring, and GitHub ingestion. Transport event-ID deduplication is distinct from Activity's source/idempotency-key deduplication. After the integration passes, replace the implementation behind `ActivityRelayAdapter`; retain the Activity domain wrapper and infrastructure responsibilities. [Activity protocol](../activity-protocol.md), [transport boundary](../../api/src/activity/activity-relay.ts).
