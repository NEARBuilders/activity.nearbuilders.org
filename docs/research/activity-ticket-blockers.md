# Activity ticket external-blocker audit

Date: 2026-09-02

## Verdict

The proposed twelve-ticket decomposition is directionally sound, and there is no unavoidable third-party technology blocker: relay client libraries, a released NEAR–Nostr integration, self-hostable relay software, Redis, inherited NEAR authentication/API keys, the existing votes plugin, and GitHub's public Events API all exist.

The statement “there are no external blockers” is nevertheless too strong for the tickets as written. Two release gates are not assigned to a ticket:

1. A production relay needs an implementation choice, hosting, DNS/TLS, persistence, backup, policy/limits, monitoring, and an operator. The Activity scope explicitly requires one reliable self-hosted relay, while the existing Nostr deployment defaults to third-party public relays ([Activity scope](https://github.com/NEARBuilders/nearbuilders.org/blob/main/ACTIVITY.md#L340-L349), [current Nostr relay defaults](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/9a1397232b829fa718e3b5530bf0133339d15692/plugins/nostr/src/index.ts#L35-L54)).
2. The released NEAR–Nostr plugin handles relay publish/query and NEAR↔Nostr binding, but it does not own the Activity service's server-custodied, AES-encrypted per-project signing-key lifecycle. Its comments service deliberately accepts pre-signed user events and does not hold user keys ([released plugin](https://github.com/NEARBuilders/nostr.nearbuilders.org/releases/tag/%40every-plugin%2Fnostr%401.0.0), [binding and relay contract](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/9a1397232b829fa718e3b5530bf0133339d15692/plugins/nostr/src/contract.ts#L72-L319), [pre-signed-event design](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/9a1397232b829fa718e3b5530bf0133339d15692/plugins/nostr/src/services/nostr.ts#L35-L60)).

These are conditional external blockers, not fundamental ones. If tickets #1 and #3 explicitly own those outcomes and the assignee has infrastructure/deployment authority, the blockers become ordinary implementation work. If the tickets merely assume another team will provide them, #1 “Blocked by: None” and #3 “Blocked by: #2” are inaccurate.

## Ticket-by-ticket dependency correction

| # | Proposed ticket | Assessment |
| --- | --- | --- |
| 1 | Deliver a relay-backed filtered activity feed | **Change required.** “Blocked by: None” is safe only if this ticket explicitly owns the relay adapter choice and a development relay. Production completion additionally depends on relay deployment authority. Its public acceptance criteria should include the custom kind/tag schema, relay acknowledgement policy, query pagination/cursors, subscription reconnect/replay, and integration tests. |
| 2 | Register and approve project sources | **Correct as foundational work.** It can use inherited session/organization/NEAR context. It should produce stable source IDs, approval state, valid event types, point values, and ownership rules consumed by #3/#4/#8. |
| 3 | Manage project signing identities and API keys | **Dependency incomplete.** Keep #2, but add the chosen Nostr binding contract/released plugin as a readiness dependency. The ticket must own project-key creation/linking, encrypted custody, key rotation, API-key-to-source mapping, explicit permissions, and revocation. |
| 4 | Ingest idempotent, signed activity events | **Mostly correct after #1/#3 are fixed.** Require a durable source-scoped idempotency record before signing/publishing; a newly constructed Nostr event can change its content hash when `created_at` changes, so relay deduplication alone is not a retry contract ([NIP-01 event ID definition](https://github.com/nostr-protocol/nips/blob/master/01.md)). |
| 5 | Stream filtered activity over SSE | **Correct dependency on #4**, but it also relies on #1's subscription/reconnect boundary. The released Nostr plugin's oRPC contract exposes publish/query but not a streaming subscribe route, although its internal core has `subscribe`; #5 must subscribe directly or extend the shared contract ([public contract](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/9a1397232b829fa718e3b5530bf0133339d15692/plugins/nostr/src/contract.ts#L248-L319), [internal subscription](https://github.com/NEARBuilders/nostr.nearbuilders.org/blob/9a1397232b829fa718e3b5530bf0133339d15692/plugins/nostr/src/nostr-core/core.ts#L72-L105)). |
| 6 | Rank actors using dynamic point values | **Add infrastructure ownership.** #4 is the correct data dependency, but #6 needs local/prod Redis provisioning, replay/reconciliation from relay history, atomic idempotent count updates, and a failure/recovery policy. |
| 7 | Moderate immutable events | **Dependency graph is reasonable.** Hiding should be a local moderation projection keyed by immutable Nostr event ID; it cannot depend on editing relay history. The existing plugin provides precedent for `hiddenAt` filtering and admin-only hide operations ([existing implementation](https://github.com/NEARBuilders/nearbuilders.org/blob/c3238b39cc19fa4661ddbb96912490743b8c499f/plugins/activity/src/index.ts#L87-L123)). |
| 8 | Surface provenance and verified weighting | **Mostly correct.** Add an explicit dependency on #3's finalized NEAR↔Nostr proof/key model, because “verified” cannot be implemented solely from source approval and leaderboard state. |

## Recommended graph change

Add one prerequisite ticket before #1 and #3, or move the following acceptance criteria into those tickets:

> **Freeze the Nostr and infrastructure boundary**
>
> - Pin the released NEAR–Nostr plugin/library and document what Activity calls versus implements locally.
> - Define the Activity Nostr kind, required tags, binding proof, and the split between user-controlled linked keys and gateway-custodied project keys.
> - Select and deploy the development/production relay, including persistence, backup, NIP-11 policy, monitoring, and operator ownership.
> - Provision local and production Redis and record the connection-secret ownership.
> - Prove publish, query, reconnecting subscription, binding verification, gateway signing, and Redis replay/reconciliation in an integration test.

Then adjust dependencies to:

- #1 → boundary/infrastructure prerequisite
- #3 → #2 + boundary/infrastructure prerequisite
- #4 → #1 + #3
- #5 → #1 + #4
- #6 → #4 + provisioned Redis acceptance
- #8 → #1 + #2 + #3 + #6
- #10 → #4 + #5 + resolved GitHub source/actor policy
- #11 → #4 + #5 + #6 + #8 + nearbuilders.org cutover ownership

## Final answer

The tickets are not fully right as written, because they hide ownership of the self-hosted relay, Activity-specific signing-key custody, GitHub attribution/scope, and the nearbuilders.org cutover. They are close: once those responsibilities are made explicit, there is no unavoidable external technology blocker. The only remaining hard blockers would be organizational—lack of infrastructure/deployment authority, production secrets, a GitHub App/token owner if authenticated polling is selected, or a nearbuilders.org maintainer to execute the cutover.
